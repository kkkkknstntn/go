# Задание 29. «Последний билет»

Разработайте сервис бронирования и покупки мест на мероприятие.

Пользователь выбирает свободное место и бронирует его на ограниченное время. Пока бронь действует, другой пользователь не должен иметь возможность забронировать или купить это же место.

После бронирования пользователь может начать покупку. Оплата моделируется внутри приложения через тестовый баланс пользователя. При успешной оплате деньги должны быть атомарно переведены с баланса пользователя на баланс организатора мероприятия.

Сервис должен корректно работать при:

- конкурентных попытках забронировать одно место;
- истечении времени брони;
- отмене брони;
- недостатке денег;
- задержанном подтверждении оплаты;
- повторном подтверждении;
- слишком позднем подтверждении;
- конкурентных операциях с балансом.

Главные гарантии системы:

> Одно место не должно быть одновременно забронировано или продано двум пользователям.

> Одни и те же деньги пользователя не должны быть потрачены дважды.

## 1. Основные сущности

Минимально система должна содержать:

```text
User
Event
Organizer
Seat
Reservation
Purchase
Payment
```

Связи:

```text
Organizer
    ↓
  Event
    ↓
   Seat
    ↓
Reservation
    ↓
 Purchase
    ↓
 Payment
```

Покупатель:

```text
User
 └── balance
```

Организатор:

```text
Organizer
 └── balance
```

---

## 2. Пользователи

Для пользователя необходимо хранить минимум:

```text
id
name
balance
```

Например:

```text
user-1
balance = 10 000
```

Для задания используется тестовый внутренний баланс.

Реальная банковская карта, эквайринг и интеграция с банком не требуются.

Пользователя можно создать через API:

```text
POST /users
```

Например:

```json
{
  "name": "Ivan",
  "balance": 10000
}
```

Баланс хранится в базе данных.

---

## 3. Организатор мероприятия

У мероприятия должен существовать организатор.

Минимально:

```text
id
name
balance
```

Например:

```text
Organizer:
concert-company

balance:
50 000
```

При успешной покупке деньги должны перейти:

```text
User.balance
      ↓
Organizer.balance
```

Деньги не должны просто исчезать после списания со счёта пользователя.

---

## 4. Мероприятие и места

Мероприятие содержит конечный набор мест.

Например:

```text
Концерт

A1
A2
A3
...
A100
```

Для мероприятия необходимо хранить минимум:

```text
id
name
organizer_id
```

Для места:

```text
id
event_id
number
price
```

Например:

```text
A17
price = 2000
```

Цена должна храниться на стороне сервера.

Клиент не должен присылать:

```json
{
  "price": 1
}
```

и тем самым самостоятельно определять стоимость покупки.

---

## 5. Просмотр мест

Пользователь должен иметь возможность получить список мест мероприятия.

Например:

```text
GET /events/{eventId}/seats
```

Ответ:

```json
[
  {
    "seat": "A1",
    "price": 2000,
    "status": "available"
  },
  {
    "seat": "A2",
    "price": 2000,
    "status": "reserved"
  },
  {
    "seat": "A3",
    "price": 2500,
    "status": "purchased"
  }
]
```

Минимальные логические состояния места:

```text
available
reserved
payment_pending
purchased
```

## 6. Создание брони

Пользователь выбирает место:

```text
A17
```

и отправляет:

```text
POST /reservations
```

Например:

```json
{
  "userId": "user-1",
  "eventId": "event-1",
  "seatId": "A17"
}
```

При успешном бронировании:

```json
{
  "reservationId": "r-123",
  "seatId": "A17",
  "status": "reserved",
  "expiresAt": "2026-09-19T15:10:00Z"
}
```

---

## 7. TTL брони

Бронь действует ограниченное время.

Например:

```text
reservation TTL = 5 минут
```

Значение должно задаваться конфигурацией.

Сценарий:

```text
12:00 → A17 reserved
12:05 → reservation expired
12:05 → A17 available
```

Если процесс покупки не был начат до окончания TTL, бронь перестаёт действовать.

---

## 8. Конкурентная бронь одного места

Пусть:

```text
A17 = available
```

Одновременно:

```text
User 1 → reserve A17
User 2 → reserve A17
```

Корректно:

```text
User 1 → success
User 2 → conflict
```

или наоборот.

Недопустимо:

```text
User 1 → success
User 2 → success
```

Операция:

```text
проверить доступность
+
создать бронь
+
закрепить место
```

должна быть конкурентно безопасной.

---

## 9. SELECT → INSERT недостаточно

Наивная схема:

```text
SELECT seat

если available:
    INSERT reservation
```

не является достаточной гарантией.

Возможна гонка:

```text
Transaction 1:
SELECT A17 → available

Transaction 2:
SELECT A17 → available

Transaction 1:
reserve

Transaction 2:
reserve
```

Необходимо использовать механизм конкурентного контроля на уровне общего состояния.

Например:

- row-level locking;
- optimistic locking;
- conditional UPDATE;
- unique constraint;
- другой корректный способ.

Выбранный механизм необходимо объяснить.

---

## 10. Постоянное хранилище

Рекомендуется использовать:

```text
PostgreSQL
```

Состояние системы должно храниться в БД.

Недостаточно защищать бронь только:

```go
sync.Mutex
```

потому что возможна архитектура:

```text
            Load Balancer
             /         \
            /           \
      Go instance 1   Go instance 2
            \           /
             PostgreSQL
```

Два экземпляра приложения должны сохранять те же гарантии.

---

## 11. Отмена брони

Пользователь может отменить действующую бронь:

```text
POST /reservations/{id}/cancel
```

Переход:

```text
reserved → canceled
```

После этого:

```text
seat → available
```

Нельзя отменить:

```text
expired
canceled
purchased
```

бронь.

---

## 12. Истечение брони

Просроченная бронь должна переходить:

```text
reserved → expired
```

после достижения:

```text
expiresAt
```

Не требуется обеспечить выполнение ровно в заданную миллисекунду.

Но после TTL просроченная бронь не должна продолжать блокировать место.

---

## 13. Background worker expiration

Необходимо реализовать background worker, который периодически находит:

```text
reserved
AND expires_at <= now
```

и переводит их:

```text
reserved → expired
```

Однако корректность системы не должна зависеть только от background worker.

Например, если worker запаздывает на несколько секунд, бизнес-логика всё равно должна учитывать:

```text
expiresAt <= now
```

при попытке использовать бронь.

---

## 14. Начало покупки

Пользователь с действующей бронью может начать покупку:

```text
POST /reservations/{id}/purchase
```

Сервис проверяет:

```text
reservation.status == reserved
now < expiresAt
reservation belongs to user
```

После этого:

```text
reserved → payment_pending
```

Создаются:

```text
Purchase
Payment
```

Например:

```json
{
  "purchaseId": "purchase-123",
  "paymentId": "payment-456",
  "status": "payment_pending",
  "amount": 2000,
  "paymentExpiresAt": "2026-09-19T15:20:00Z"
}
```

---

## 15. Reservation TTL и Payment timeout

После перехода:

```text
reserved → payment_pending
```

обычный TTL брони больше не применяется.

Вместо него начинает действовать отдельный:

```text
payment timeout
```

Например:

```text
reservation TTL = 5 min
payment timeout  = 10 min
```

Это означает:

```text
12:00 → reserved
12:04 → payment_pending
12:05 → обычный reservation TTL закончился
```

Но место продолжает принадлежать текущей покупке.

До:

```text
12:14 → payment timeout
```

---

## 16. Модель оплаты

Настоящая банковская интеграция не требуется.

Оплата моделируется внутри приложения.

Существует:

```text
User.balance
Organizer.balance
Seat.price
```

Например:

```text
User.balance      = 10 000
Organizer.balance = 50 000

Seat.price = 2 000
```

При успешной оплате:

```text
User.balance:
10 000 → 8 000

Organizer.balance:
50 000 → 52 000
```

---

## 17. Payment

Для каждой попытки оплаты необходимо хранить минимум:

```text
id
purchase_id
user_id
organizer_id
amount
status
created_at
expires_at
completed_at
```

Минимальные состояния:

```text
pending
succeeded
failed
timed_out
```

---

## 18. Подтверждение оплаты

Для имитации платёжного подтверждения реализуйте тестовый endpoint:

```text
POST /payments/{paymentId}/confirm
```

Он моделирует callback от внешней платёжной системы.

Это не означает:

```text
клиент сам устанавливает purchased=true
```

Endpoint должен запускать настоящую бизнес-операцию оплаты:

```text
проверить состояние payment
↓
проверить timeout
↓
проверить баланс пользователя
↓
списать деньги
↓
зачислить деньги организатору
↓
payment → succeeded
↓
purchase → purchased
```

---

## 19. Атомарный перевод денег

Успешное подтверждение должно выполняться в одной транзакции.

Например:

```text
BEGIN

проверить:
payment == pending

проверить:
now < payment.expiresAt

проверить:
User.balance >= amount

User.balance -= amount

Organizer.balance += amount

Payment.status = succeeded

Purchase.status = purchased

COMMIT
```

Если любая операция завершается ошибкой:

```text
ROLLBACK
```

Недопустима схема:

```text
1. списали деньги у User
2. COMMIT

3. попытались начислить Organizer
4. ошибка
```

При таком подходе деньги пользователя исчезнут.

---

## 20. Недостаточно средств

Если:

```text
User.balance = 500
Seat.price   = 2000
```

оплата должна завершиться:

```text
payment_pending → failed
```

Причина:

```text
insufficient_funds
```

Деньги не списываются.

Организатор ничего не получает.

Место снова становится доступным.

---

## 21. Ошибка оплаты

Также должен существовать тестовый сценарий:

```text
POST /payments/{paymentId}/fail
```

Он моделирует отказ платёжной системы.

После него:

```text
payment → failed
purchase → failed
seat → available
```

Деньги не перемещаются.

---

## 22. Успешная покупка

После успешного подтверждения:

```text
payment → succeeded
purchase → purchased
```

Место окончательно продано.

Его больше нельзя:

```text
reserve
purchase again
```

---

## 23. Задержанное подтверждение

Обязательный сценарий:

```text
12:00 → reserved

reservation expires:
12:05

12:04 → payment_pending

payment expires:
12:14

12:10 → confirm
```

Подтверждение должно успешно завершить покупку:

```text
payment_pending → purchased
```

Несмотря на то, что исходный reservation TTL уже прошёл.

---

## 24. Слишком позднее подтверждение

Сценарий:

```text
12:04 → payment_pending

payment timeout:
12:14

12:14 → timed_out
```

После timeout место освобождается.

Например:

```text
12:15 → User 2 резервирует A17
```

Затем:

```text
12:20 → приходит старый confirm User 1
```

Такой callback должен быть отклонён.

Недопустимо:

```text
timed_out → purchased
```

Деньги также не должны переводиться.

---

## 25. Идемпотентность подтверждения

Один callback может прийти несколько раз:

```text
confirm payment-456
confirm payment-456
confirm payment-456
```

Первый успешный вызов:

```text
User.balance      -= 2000
Organizer.balance += 2000
Payment           → succeeded
Purchase          → purchased
```

Повторные вызовы не должны:

```text
ещё раз списывать деньги
ещё раз начислять деньги
создавать вторую покупку
```

Система должна обработать повторное сообщение идемпотентно.

---

## 26. Двойная трата одного баланса

Отдельная конкурентная задача.

Пусть:

```text
User.balance = 2000
```

Пользователь пытается одновременно купить:

```text
A1 = 2000
A2 = 2000
```

Конкурентно приходят:

```text
confirm payment-1
confirm payment-2
```

Недопустимо:

```text
payment-1 = succeeded
payment-2 = succeeded

User.balance = -2000
```

Корректно:

```text
один payment → succeeded
второй payment → insufficient_funds
```

Итог:

```text
User.balance = 0

Organizer.balance увеличился только на 2000
```

---

## 27. Гонка cancel vs purchase

Одновременно:

```text
cancel reservation
```

и:

```text
start purchase
```

Допустим только один результат:

```text
canceled
```

или:

```text
payment_pending
```

Недопустимо одновременно считать бронь отменённой и покупку начатой.

---

## 28. Гонка expiration vs purchase

Пусть:

```text
expiresAt = 12:05:00
```

Практически одновременно:

```text
worker → expire
```

и:

```text
user → purchase
```

Система должна прийти ровно к одному состоянию:

```text
expired
```

или:

```text
payment_pending
```

---

## 29. Гонка payment timeout vs confirm

Одновременно:

```text
worker → payment timeout
```

и:

```text
payment confirm
```

Результатом должно стать ровно одно финальное состояние:

```text
purchased
```

или:

```text
timed_out
```

Недопустимо:

```text
payment timed_out
```

и одновременно:

```text
деньги списаны
```

## 33. Основная state machine

```text
available
    ↓ reserve
reserved
    │
    ├── cancel ───────────→ canceled
    │
    ├── expire ───────────→ expired
    │
    └── start purchase
              ↓
       payment_pending
              │
              ├── confirm + money transfer
              │          ↓
              │       purchased
              │
              ├── fail
              │    ↓
              │  failed
              │
              └── timeout
                   ↓
                timed_out
```

---

## 34. Движение денег

Деньги перемещаются только при:

```text
payment pending → succeeded
```

Правила:

```text
confirm:
User → Organizer

fail:
денег не двигаем

timeout:
денег не двигаем

late confirm:
денег не двигаем

duplicate confirm:
повторно денег не двигаем
```

---

## 35. Финальные состояния

Финальными считаются:

```text
Reservation:
canceled
expired

Purchase:
purchased
failed
timed_out

Payment:
succeeded
failed
timed_out
```

После финального перехода нельзя произвольно изменить состояние.

Например:

```text
purchased → canceled
```

не допускается.

---

## 36. Освобождение места

Место снова становится доступным после:

```text
reservation canceled
reservation expired
payment failed
payment timed_out
```

После:

```text
purchased
```

место остаётся окончательно занятым.

## 38. HTTP API

Frontend не требуется.

Для демонстрации достаточно Swagger/OpenAPI.

Минимальный API:

```text
POST /users
GET  /users/{id}

GET  /events
GET  /events/{id}/seats

POST /reservations
GET  /reservations/{id}
POST /reservations/{id}/cancel
POST /reservations/{id}/purchase

GET  /purchases/{id}

GET  /payments/{id}
POST /payments/{id}/confirm
POST /payments/{id}/fail
```

Желательно предоставить:

```text
GET /organizers/{id}
```

чтобы на защите можно было увидеть изменение баланса организатора.

---

## 39. HTTP Conflict

Попытка забронировать занятое место должна возвращать понятную ошибку.

Например:

```text
409 Conflict
```

Некорректные переходы состояний также должны обрабатываться явно.

---

## 40. Background workers

Необходимо реализовать обработку:

```text
reservation expiration
payment timeout
```

Например, периодический worker:

```text
каждые 5 секунд
```

находит:

```text
reserved
AND expires_at <= now
```

и:

```text
payment_pending
AND payment_expires_at <= now
```

Однако worker не является единственной защитой TTL.

---

## 41. Несколько экземпляров приложения

Решение должно оставаться корректным:

```text
             Load Balancer
              /         \
             /           \
       Go instance 1   Go instance 2
             \           /
              PostgreSQL
```

Должны сохраняться гарантии:

```text
одно место → один владелец
```

и:

```text
один баланс → нельзя потратить дважды
```

## 42. Транзакции

### Бронирование

```text

+

```

### Начало покупки

```text
проверка reservation
+
создание purchase
+
создание payment
+

```

```text
проверка Payment
+

+
проверка balance
+

+

+

+

```

В README необходимо описать границы транзакций.

```text
1 available seat
```


## 44. Конкурентный эксперимент №2 — один баланс

Создайте пользователя:

```text
balance = 2000
```

Две покупки:

```text
A1 = 2000
A2 = 2000
```

Одновременно выполните два:

```text
payment confirm
```

Ожидается:

```text
1 succeeded
1 failed: insufficient_funds
```

Баланс:

```text
User = 0
```

Организатор получает только:

```text
2000
```

## 45. Конкурентный эксперимент №3 — граница TTL

Создайте бронь:

```text
TTL = 5 секунд
```

На границе TTL конкурентно выполните:

```text
expire
```

и:

```text
start purchase
```

Повторите много раз.

Каждый запуск должен завершаться одним допустимым состоянием.

## 46. Конкурентный эксперимент №4 — timeout vs confirm

Создайте:

```text
payment timeout = 5 секунд
```

На границе timeout одновременно выполните:

```text
confirm
```

и:

```text
timeout
```

Допустимо:

```text
purchased
```

или:

```text
timed_out
```

Недопустимо:

```text
timed_out + деньги переведены
```

## 47. Производительность и contention

Необходимо понимать, где появляются hotspots.

Например:

```text
1000 клиентов
     ↓
одно последнее место
```

Все конкурируют за один ресурс.

Другой сценарий:

```text
100 payment confirmations
       ↓
один User.balance
```

Все конкурируют за одну строку пользователя.

На защите необходимо объяснить:

- где возникают блокировки;
- какие транзакции ждут;
- какие получают конфликт;
- почему не возникает двойной продажи;
- почему баланс не уходит в минус.

## 48. Context и timeout

HTTP-запросы должны использовать:

```go
context.Context
```

Операции с БД должны выполняться с context.

Отмена HTTP-запроса не должна оставлять частично выполненную транзакцию.

## 49. Graceful shutdown

Приложение должно корректно обрабатывать:

```text
SIGINT
SIGTERM
```

При остановке необходимо:

1. перестать принимать новые запросы;
2. остановить background workers;
3. дать активным запросам завершиться в пределах timeout;
4. откатить незавершённые транзакции;
5. закрыть соединения с БД;
6. завершить приложение.

---

## 50. Перезапуск приложения

После restart данные не должны теряться.

Например:

```text
reserved
expiresAt < now
```

не должна считаться активной только потому, что worker после старта ещё не успел её обработать.

Аналогично:

```text
payment_pending
paymentExpiresAt < now
```

не должна принимать новый успешный confirm.

```text

```

### Недостаточно средств

```text

→ payment failed

```

```text

→ timed_out
→ деньги не двигаются
→ место освобождается
```

```text

→ confirm
→ отклонён
→ деньги не двигаются
```

### Duplicate confirm

```text
confirm
confirm
confirm
```

Деньги переводятся только один раз.

### Double spending

```text
balance = 2000

payment A = 2000
payment B = 2000

confirm одновременно
```

Успешна только одна оплата.

Конкурентно:

```text
cancel
purchase
```

Результат всегда консистентный.

### Expire vs purchase

Конкурентно:

```text
expire
purchase
```

Результат всегда консистентный.

### Timeout vs confirm

Конкурентно:

```text
timeout
confirm
```

Ровно одно финальное состояние.
